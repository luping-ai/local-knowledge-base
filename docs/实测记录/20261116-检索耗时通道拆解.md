# 检索耗时的通道拆解（16016 块）

- **日期**：2026-11-16
- **目的**：定位"检索 469 ms"到底花在哪，为 §10.5 的性能目标提供依据
- **工具**：`tools/bench_scale.py`（主测量）+ 两个一次性探针（已删除，方法记录在下）

---

## 0. 一句话结论

| 通道 | 16016 块 | 296 块 | 随规模的增量 |
| --- | --- | --- | --- |
| `keyword`（纯 FTS5） | **204 ms** | 86 ms | **+118 ms**（规模相关） |
| `semantic`（多出的部分） | ~150 ms | ~23 ms | +127 ms |
| `hybrid`（RRF 合并） | **469 ms** | 140 ms | +329 ms |

**两处推翻原有认知**：

1. **keyword 通道本身就随规模变慢**（86 → 204 ms）。之前的估算把 FTS5 当成
   "固定几毫秒"，实际它有明显的规模相关性。
2. **`< 50 ms` 的检索目标不可能达成**，`< 300 ms` 也不成立。真实数字是
   1.6 万块 469 ms、10 万块预计更高。

---

## 1. 为什么这个拆解必须先做

`bench_scale.py` 量出的 469 ms（16016 块）是个总数，而它可能来自三处：

- FTS5 查询（keyword 通道）
- query 向量化（一次 HTTP 到 embedding 引擎）
- 16016 × 384 维的向量扫描 + 80 条元数据的 SQL

不知道该修哪个，就不知道该不该动代码。而分通道测量**只要改一个参数**
（`mode=`），不需要改 Runtime。

---

## 2. 方法

### 2.1 三通道分别计时

SDK 的 `SearchRequest` 有 `mode` 参数，直接指定：

```python
conn.call(lambda c: c.search(SearchRequest(
    query="保修期是多久", kb_ids=[kb_id], top_k=20, mode="keyword")))
```

先预热一次（排除首次连接/索引载入），再连续 6 次取中位数。

### 2.2 为什么用"keyword 单独测"定位规模效应

**向量化 16016 块要 28 分钟，而入库只要 19 秒。** keyword 通道完全不依赖
向量，所以"只入库、不向量化、只测 keyword"能在 35 秒内走完 4 个规模档位：

```
2002 块   → 110 ms
5005 块   → 109 ms
10010 块  → 156 ms
16016 块  → 204 ms
```

这条曲线直接证明规模效应在 FTS5 侧，与向量无关。**这是本轮最省时间的一个
实验设计**——把一个需要 2 小时的实验变成 35 秒。

## 3. 数据

### 3.1 296 块（`localkb-dev`，热态）

| 模式 | 中位数 | 范围 |
| --- | --- | --- |
| keyword | 86 ms | 78~109 |
| semantic | 109 ms | 78~140 |
| hybrid | 140 ms | 109~157 |

`top_k` 的影响很小（1→50 只从 117 到 156 ms），说明**固定开销占主导**。

query 长度有影响：2 字 188 ms、29 字 266 ms（在 hybrid 下）——长的 query
在 FTS5 侧构造更复杂。

### 3.2 16016 块（热态，3 轮 × 5 query + 3 次同 query）

| 项 | 值 |
| --- | --- |
| 冷启（首次，含 `LoadIndex`） | 688 ms |
| **热（中位数）** | **469 ms** |
| 热（范围） | 406~547 ms |
| 冷启与热之差 | **仅 219 ms** |

**冷启只比热慢 219 ms**，这本身是重要信息：说明 `LoadIndex` 很快
（`bench_scale` 里 16016 × 384 维向量载入 + 建索引远低于 1 秒），
慢的是**每次查询的固定成本**。

第 2、3 轮的"冷启"分别是 485 / 422 ms——与热态几乎无差别，说明索引
一直驻留，没有在查询之间被释放。

## 4. 结论与建议

### 4.1 性能目标必须改

| 原目标 | 实测 | 建议 |
| --- | --- | --- |
| 检索 < 50 ms | 296 块就要 140 ms | **删除这条**，不可能达成 |
| 检索 < 300 ms | 16016 块 469 ms | 改为**分档**，见下 |

**建议的分档目标**（按实测外推，10 万块数据待补）：

| 库规模 | 检索目标 | 依据 |
| --- | --- | --- |
| < 5000 块 | < 200 ms | 2002 块 keyword 110 ms + 语义部分 |
| 5000~2 万块 | < 600 ms | 16016 块实测 469 ms，留余量 |
| 2 万~10 万块 | 待测 | 本轮 10 万块运行中 |

### 4.2 UI 必须给出可感知的反馈

469 ms 已经超过"瞬时"的心理阈值（约 200 ms）。所以检索/提问时：

- 不能是"点了没反应"——必须有"正在检索…"的可见状态
- 10 万块预计 1.5~2.5 s，需要**进度感**而非单纯转圈

### 4.3 可优化项（按投入产出排序）

| 项 | 预期收益 | 代价 | 判断 |
| --- | --- | --- | --- |
| FTS5 加 `LIMIT` 或改 `bm25` 排序策略 | 可能减 50~100 ms | 改 Go + 重新标定 | **值得做**，但需单独评估召回影响 |
| `chunkMeta` 批量查询优化 | 几十 ms | 小 | 可做 |
| 向量索引换 ANN | ~0（扫描本身很快） | 大（见 `vector.go` 注释：本项目规模下暴力更快） | **不做** |
| query embedding 缓存（相同 query 复用） | 命中时省 ~50 ms | 小 | 可做，但要考虑内存 |

**关键判断：不要动向量索引。** `vector.go` 的实现（连续 `[]float32` + 8 路
并行）在 1.6 万块下的扫描成本可以忽略——证据是"冷启与热只差 219 ms"，
如果扫描是瓶颈，冷启不会这么接近热态。

---

## 5. 顺带验证的事实

| 事实 | 数据 |
| --- | --- |
| 索引会驻留，不会在查询间释放 | 第 2、3 轮"冷启" 485/422 ms ≈ 热态 469 ms |
| `LoadIndex` 很快 | 16016 块冷启只比热多 219 ms |
| 入库内存开销 | 16016 块 +58 MB（块文本 + FTS5 索引） |
| 向量内存开销 | 16016 块 +66 MB（约 0.004 MB/块） |
| 向量化速度（16k 规模） | 9.6 块/秒（低于 500 块基准的 11.6，规模效应） |
| `top_k` 影响小 | 296 块库 1→50 只从 117 到 156 ms |
