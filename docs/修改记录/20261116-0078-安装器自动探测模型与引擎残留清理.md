- **状态**：已落地

## 2. S8 + S10：安装器自动探测（`cmd/localai-installer/main.go`）

### 改动

`runtimeArgv` 从"只拼 serve + -enable-admin + -llama-server"扩展为自动探测：

| 探测项 | 条件 | 加的参数 |
| --- | --- | --- |
| 模型目录 | `installDir/models` 存在 | `-models <绝对路径>` |
| Embedding | `models/multilingual-e5-small-q8_0.gguf` 存在 | `-embedding-model <绝对路径>` |
| 预加载 | 按固定优先级找到合格模型 | `-preload <模型ID>` |

### 三个刻意的决定

**① `-models` 必须显式给。** 不给时 Runtime 的 `resolvePath` 相对 exe 目录
解析 `models`。安装器把模型放在 `installDir/models`、exe 也在 `installDir`，
看起来一致——但用户从别的 cwd 启动（开始菜单的 `gui.bat` 会 cd）时，
相对路径就落到别处，表现为 `/models` 里 `present` 全是 false。

**② 预加载按固定顺序挑，不挑"目录里第一个 gguf"。** 实测清单里有 9 个模型，
随便挑会挑到 350M 的 granite/LFM——那些 `rag.qualified=false`（RAG 达标率
不合格）。用户拿到"能跑但答不准"的模型，比"没有可用模型"更糟，因为他会
以为程序正常。

优先级：`qwen2.5-1.5b-instruct-q4` → `qwen2.5-3b-instruct-q4`。
依据 `docs/实测记录/20261112-大模型RAG能力实测.md`（1.5b 是 8GB 基线；
3b 需 3.1 GiB，16GB 可用）。更大的（qwen3-4b）不自动选——让用户去后台换。

**③ 探测失败不加参数，不报错。** 文件不存在时 Runtime 以"无语义检索"或
"无预加载"正常启动。这比启动失败好：用户至少能用关键词检索，并能从桌面端
的提示里知道该去后台配什么。

### 验证

```
$ go test ./cmd/localai-installer -run TestRealInstallDirArgv -v
实际参数: [serve -enable-admin -llama-server ...\llama-server.exe
           -models ...\models
           -embedding-model ...\models\multilingual-e5-small-q8_0.gguf
           -preload qwen2.5-1.5b-instruct-q4]
--- PASS
```

运行期（重启后不调 `load_model`）：

```
active_model: qwen2.5-1.5b-instruct-q4       ← S10
vectorize.model: multilingual-e5-small-q8_0  ← S8
chunks/embedded: 296 / 296
```

## 3. S11：`stop` 不清引擎子进程（真缺陷）

### 现象

`localai-cli-installer.exe stop` 之后任务管理器里仍有 `llama-server.exe`：

```
   Id   MB
25080 1656
25940  209
```

它们属于**已经退出**的 Runtime。后果是下一次 `start`：

```
可用内存 1.3 GiB，连最小的模型都需要 1.9 GiB → level=rule_only
```

而 `rule_only` 会让知识库端点不注册 → 桌面端所有 `/knowledge/*` 报 404。

### 根因

Runtime 用 `Job Object` + `KILL_ON_JOB_CLOSE` 管引擎，但 **Job 施加可能失败**：

```
{"event":"engine_limit_warning",
 "detail":"无法为引擎施加内存硬限额: AssignProcessToJobObject(13460) failed: Access is denied."}
```

引擎不在 Job 里时，`TerminateProcess` 杀父进程与它无关。而 `stopRuntime`
原本只按 exe 路径停 `launcher` 与 `localai-cli`，**没有处理 `engines/` 下的引擎**。

### 修复

新增 `killEngines(installDir)`：

- 遍历 `engines/*/llama-server.exe`（不写死 `llama-cpu`——引擎布局会演进到
  vulkan/cuda，写死一个目录会在换引擎时静默失效，而失效的表现是"内存莫名
  被占满"，极难联想到残留进程）
- 按**完整路径**匹配进程，只清本安装目录的（用户可能同时跑开发版引擎）
- 在 Runtime 退出后、等待文件句柄释放前调用；超时路径也调用一次

**实测有效**：`stop` 后两个残留（1656 MB + 209 MB）都被清掉，下次 `start`
的内存恢复正常。

## 4. S12：`capability` 是启动快照（真缺陷）

### 现象

实测序列：

1. 残留引擎占满内存 → 新实例判定 `rule_only`
2. 手工杀掉残留进程 → 内存从 1.3 GiB 升到 4.6 GiB
3. `/api/v1/capability` **仍然**返回 `rule_only`
4. 桌面端据此禁用知识库 → 用户以为"知识库不见了"

### 为什么原设计不成立

`CapabilityStatus` 的注释写着"在启动时确定"。但**内存会变**：关掉 IDE、
关掉浏览器、关掉残留引擎，可用内存就从 1.2 GiB 涨到 4.6 GiB。能力评估
依赖可用内存，因此它也必须能变。

### 修复

```go
assessNow := func() degrade.CapabilityReport {
    return degrade.AssessCapability(catalog.List(), currentAvailableMemory())
}
capReport := assessNow()          // 启动时一次，仅用于打印横幅
deps.Capability = func() api.CapabilityStatus {
    cur := assessNow()            // 每次请求重算
    ...
}
```

代价可忽略：`AssessCapability` 只是遍历模型清单（10 项以内）加一次内存查询，
远小于一次 HTTP 往返。

## 5. S13：内存不足时连知识库一起关掉（真缺陷）

### 现象

`serve.go` 原本：

```go
if !capReport.RAGEnabled() { 跳过 } else { initKnowledge(...) }
```

而 `RAGEnabled()` 要求 `level == full`——"内存够加载生成模型"。

内存紧张时**知识库端点全部 404**，桌面端 `kb_stat` 报：

```
404 no such endpoint: /api/v1/knowledge/bases/kb_.../stats
```

### 为什么这是错的

**知识库本身只依赖 SQLite 与 FTS5，不需要模型内存。** 用户即便模型加载不了，
也应该能查看库里的文档、用关键词检索、删除文档。

而 `initKnowledge` 内部已经能优雅处理"无 Embedding"——`startEmbeddingEngine`
失败时只 `log.Warn` 并返回只有 SQLite 的 runtime。

### 修复

判据从 `!RAGEnabled()` 改为 `Level == CapabilityRuleOnly`。`rule_only` 才是
"连基准模型都装不下"的极端状态；`chat_only`（能加载模型但不是 RAG 合格模型）
应保留知识库能力。

**验证**（`level=rule_only`、可用 1.61 GiB 时）：

```
KB endpoints OK — docs: 3 chunks: 296 embedded: 296
```

修复前这里会返回 404。

## 7. 一个方法论层面的收获

这一批 5 项里有 **4 项是"单测全绿但产品是坏的"**：

- S10/S11/S12/S13 都属于"代码逻辑正确、单元测试通过，但端到端跑就露馅"
- 它们的共同点是**依赖运行环境的状态**（模型有没有加载、内存够不够、
  有没有残留进程），而单元测试里这些状态是假定的

唯一能发现它们的方法是**真的装一遍、真的重启、真的看任务管理器**。
这也是方案 §14 把 M5 的验收定为"干净虚拟机装完即用"的原因——那不是
形式主义，而是这类缺陷的唯一捕网。

## 7.1 修复没部署就等于没修（实测踩到）

S11 修完之后，`go test` 全绿、`go run ./cmd/localai-installer stop` 也验证
有效。但过一会儿检查进程列表，**又有 4 个 `llama-server`**：

```
ProcessId ParentProcessId   MB CreationDate
    29108           23220  209 12:59:20     ← 父进程 23220 已死（残留）
     8436           23220 1656 12:59:21     ← 同上
    11744            7128  209 13:01:06     ← 父进程 7128 存活（当前实例）
    11104            7128 1687 13:03:33     ← 同上
```

原因是：我更新了 `%LOCALAPPDATA%\Programs\LocalAIHub\localai-cli.exe`
（Runtime），但 **`stop` 是由 `localai-cli-installer.exe` 执行的**，
而那个二进制还是 11:00 的旧版（没有 `killEngines`）。

对照 `LastWriteTime` 才看出来：installer 是 `11:00:43`，新编译的是 `12:55:24`。

**这类"修了但没生效"的排查成本极高**：因为你会反复怀疑修复本身
（是不是遍历路径写错了？是不是进程匹配失败？），而真相是那段代码
根本没在跑。

**教训**：验证"修复有效"必须先确认"修复在跑"。判据是**二进制的修改时间**
而不是"我刚编译过"。M5 的版本锁定（§13.4）正是为这类问题准备的。

替换新版 installer 后实测：`stop` 清掉全部 4 个引擎，`start` 后正好 2 个
（生成 + Embedding），`level=full`。
