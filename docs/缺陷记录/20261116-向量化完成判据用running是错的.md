# 向量化完成的判据用"任务是否在跑"是错的

- **日期**：2026-11-16
- **类型**：缺陷记录（**未修**，建议 M6 前处理）
- **严重度**：中 —— 中止/取消后 UI 会显示"向量已就绪（16000/100000）"这种自相矛盾的"成功"
- **发现方式**：跑 10 万块规模标定时核对完成判据

> **一条被推翻的判断（记在这里避免重复踩）**
>
> 最初怀疑"`VectorizeAsync` 的 30 分钟硬超时会让 10 万块卡在 1.6 万块"。
> 实测到 17856 块时仍 `running=True`（约 31 分钟），**假设被证伪**。
>
> 原因是实际走的是**任务管理器**路径（`internal/api/knowledge.go` 的
> `submitTask`），而 `internal/tasks/manager.go:221` 用的是
> `context.WithCancel(context.Background())` —— **没有超时**。
> 那个 30 分钟的 `WithTimeout` 只在"未注入任务管理器"的降级路径上。
>
> 教训：读到一处 `WithTimeout(30m)` 就下结论是不够的，必须确认**实际执行路径**
> 走的是哪一条分支。这次是靠实测数据推翻的，不是靠读代码。

---

## 1. 仍成立的缺陷

`localkb/scan/job.py:487`：

```python
vp = st.vectorize
if vp is None or not vp.running:
    return True, f"向量已就绪（{st.embedded_count}/{st.chunk_count}）"
```

**`not running` 被当成"成功"**，而正确的判据是 `embedded_count == chunk_count`。

### 什么时候会误报

| 场景 | 服务端状态 | 桌面端判定 |
| --- | --- | --- |
| 用户点"取消任务" | `running=false`，只完成一部分 | ✅ 返回 True，"向量已就绪（16000/100000）" |
| Runtime 重启 | 进度丢失，`running=false` | 同上 |
| 向量化中途出错 | 任务 failed，`running=false` | 同上 |
| 模型/引擎崩溃 | 同上 | 同上 |

提示文案 **"向量已就绪（16000/100000）"** 本身自相矛盾——用户看到"就绪"
却又有两个不相等的数字。而这会让人误以为"这个库就是没这段内容"，
而不是"这段内容没被索引"。

### 为什么一直没暴露

| 阶段 | 为什么没发现 |
| --- | --- |
| M2 单测 | 用假连接，`running` 直接返回 False，测试断言的是"返回 True" |
| M2 实测（A1：296 块） | 33 秒跑完，从未进入中止路径 |
| M5 内存标定（5.9 万块） | 只向量化 9440 块就进入下一步，没检查计数 |
| 10 万块标定 | 正常跑完（任务管理器无超时），也没触发中止 |

**这条只有在"中止/取消 + 大库"同时成立时才会显现。**

## 2. 修法（未实施）

```python
if vp is None or not vp.running:
    if st.embedded_count < st.chunk_count:
        # 中止/取消/失败：不是成功，但也不是数据损坏——
        # 已完成的可用，重新触发会从断点继续（服务端 pendingChunks 只看缺向量的）
        return False, (
            f"语义索引未完成（{st.embedded_count}/{st.chunk_count}）。"
            "已完成的切片可用于语义检索；再次扫描会继续补齐剩余部分。"
        )
    return True, f"向量已就绪（{st.embedded_count}/{st.chunk_count}）"
```

**判据必须是"计数是否相等"，不能是"任务是否在跑"。**

## 3. 验收用例（建议补）

| 用例 | 通过条件 |
| --- | --- |
| 向量化中途点"取消" | UI 显示"未完成 x/y"并说明可继续，**不是**"已就绪" |
| 向量化中途重启 Runtime | 同上；再次触发只补剩余 |
| 正常完成 | `embedded == chunks` 时显示"已就绪（N/N）" |

## 4. 这类问题的通用形态

「用**过程状态**代替**结果状态**判断成功」是很容易犯的一类错误：

| 别处可能的样子 | 正确判据 |
| --- | --- |
| `not task.running` → 成功 | `done == total` |
| `process.exited` → 成功 | `exit_code == 0` |
| `http 200` → 有数据 | 响应体非空且字段齐全 |
| `file.exists()` → 写完 | 大小与校验和匹配 |

本项目里已经踩过两次同类问题（另一次是"删了文件但下次扫描又导回来"——
用"记录不存在"代替"已排除"）。值得在 M6 的代码审查里专门搜一遍
这类"用中间状态推断终态"的写法。
