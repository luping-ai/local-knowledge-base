## 2. 三个真实缺陷（都在实现过程中被测试抓到）

这三条都不是设计问题，是"写的时候以为对、跑起来才知道错"的类型。记下来是因为
它们各自都有一个**极具误导性的症状**。

### 2.1 唤醒 Runtime 时轮询不重建 Client → 必然超时

**症状**：手动 `installer stop` 后启动 LocalKB，界面一直转圈，20 秒后报
"本地服务启动超时"。而同时：
- 安装器输出"已启动"
- `runtime.json` 已被更新为新端口
- 手工 `curl` 那个新端口是通的

**根因**：

```
Runtime 停止 → Client() 的 discover 回落到默认端口 18765（token 为空）
唤醒成功   → Runtime 拿到随机端口，例如 62481
旧 client  → 记着 18765，live() 永远 False
```

第一版轮询写的是 `if self.alive(): ... else: sleep()`，用的全是同一个旧 client。

**修复**：轮询时每轮 `_rebuild(force=True)`。实测 27.7 秒失败 → 5.5 秒成功。

**回归测试**：`test_ensure_alive_rebuilds_while_polling`
（用"重建次数 < 1 时 alive() 返回 False"模拟同构场景，不真的重启 Runtime）

### 2.2 `deleteLater()` 后 Python 包装器仍在 → 关窗口崩溃

**症状**：跑完一次扫描、然后关窗口，程序崩溃：

```
RuntimeError: Error calling Python override of QMainWindow::closeEvent():
libshiboken: Internal C++ object (ScanWorker) already deleted.
```

**根因**：`QThread.finished` 里调 `deleteLater()` 销毁了 C++ 对象，但
`self._scan_worker` 这个 Python 引用还在。`closeEvent` 里读 `isRunning()` 就炸。

**修复**：清理回调里先把持有点置空（`self._scan_worker = None`），并加
`_worker_alive()` 把"可能已销毁"的判断收在一处。

**回归测试**：`test_scan_runs_through_ui`（以 `win.close()` 结尾，崩了就该测试失败）

### 2.3 路径存归一化形式 → 界面显示全小写

**症状**：测试断言"missing 列表里的 path 应等于原路径"失败，实际返回
`c:/users/lenovo/...`。

**根因**：`local_files.path` 既承担"唯一约束"又承担"展示"。归一化（小写）
满足了前者，破坏了后者——用户看到 `d:/工作/合同.pdf` 会怀疑这不是自己的文件。

**修复**：拆成两列。`path` 存原样（展示、打开用），`path_key` 存归一化
（唯一约束用）。`scan_roots` 同样处理。

## 3. 几个刻意的设计选择

### 3.1 文件去向是三态，不是布尔

`walker._classify` 返回 `KEEP / SKIP / IGNORE`：

- `KEEP` 进 files，后续解析
- `SKIP` 进 skipped，UI 展示原因
- `IGNORE` 什么都不做

第一版只有"要/不要"，结果 `.exe`、`.png` 全被收进 files（下游才逐个失败）。
反过来让它们进 skipped 时，用户选 C 盘会看到十万条"不支持的格式"，把真正的
失败原因淹没掉。

### 3.2 内置排除项要能关

`Walker(use_default_excludes=False)`。两个用途：

1. **测试**：pytest 的 `tmp_path` 在 `%LOCALAPPDATA%\Temp` 下，而
   `/appdata/local/temp` 正是内置排除项——不开这个开关，所有遍历测试都扫不到文件。
2. **用户**：高级设置里"我就是要扫这个目录"。

这个开关是被测试逼出来的，但它同时解决了一个真实的产品需求。

### 3.3 进度分两阶段

`WALKING`（分母未知，显示"已发现 N 个"）→ `HASHING`（分母已知，显示百分比）。

合成一个进度条会让"卡在 30%"变成常态——而实际那是在算 sha256（大文件每 MB
都要读）。分阶段之后，用户能看出"现在慢在哪里"。

### 3.4 扫到但没扫到的文件不算 missing

`_find_missing` 里多了一个 `Path(row.path).exists()` 判断：文件**还在**、只是
不在当前扫描根下（用户移除过一个目录）→ 不算 missing。

这不是吹毛求疵：把"范围变化"报成"文件丢失"会让用户以为自己的资料被删了。

## 4. 与方案文档的偏差

| 方案原写 | 实际实现 | 原因 |
| --- | --- | --- |
| `runtime_supervisor.py`（spawn/wait/stop） | `runtime_conn.py`（探活/唤醒/重建） | 方案 v1.1 已删掉 spawn，文件名随之改 |
| `local_files.status` 12 种 | 同，但新增 `importing` 之外还保留了 `orphaned` / `missing` 的区分 | `orphaned` = 服务端没有这条 doc_id；`missing` = 磁盘上没有这个文件。两者处理方式不同（前者重导、后者问用户） |
| 无 `path_key` | 增加该列 | 见 §2.3 |
