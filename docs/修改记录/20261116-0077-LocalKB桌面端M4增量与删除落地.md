## 3. 四个真实缺陷

### 3.1 "从知识库移除"后，下次扫描又把它导回来

**这是最严重的一个。**

早期实现里"移除"= `delete_document()` + 删掉 `local_files` 行。而**文件还在磁盘上**，所以下次扫描按"新增"又导了一遍。

用户看到的现象是"我删了它，它又回来了"——只会以为删除功能坏了。

**修复**：新增 `local_files.status = "excluded"`。删除时**不删本地行**，而是标记为排除：
- 扫描时直接跳过（`_classify` 里判 `excluded`）
- 内容变了也不导（用户可能只是编辑了这个他不想入库的文件）
- `_persist` 不覆盖这个状态（否则下轮又变回 pending）

方案 §7.7 没有定义这个状态，是实测暴露出来的。

### 3.2 `_is_stable` 对不存在的文件返回 False → 变更永久卡住

第一版对 `stat()` 失败返回 False，于是 `pop_ready` 不断重置计时、**永不取出**。

受影响的是"写完后立刻被删/改名"的事件——临时文件、快速改名都会触发。表现是待处理队列只增不减。

**修复**：不存在视为"稳定"（它是终态）。调用方拿到变更后发现文件不在，按删除处理——`scan/job.py` 的 diff 已经覆盖这条路径。

### 3.3 MOVED 被后续 MODIFIED 覆盖 → 改名变成"删一个 + 新增一个"

编辑器改名后常会再写一次缓冲（触发 `modified`）。若让 `modified` 覆盖 `MOVED`，改名会被当成内容修改：库里留着旧名文档、同时新增一份新名的。

**修复**：`merge` 里 `CREATED` 与 `MOVED` 都是"强"类型，不被后续的 `modified` 覆盖。

### 3.4 SQLite 外键（M3 已修，本阶段加深理解）

已在上阶段修复，这里记一笔因为它同类：**"看起来成功的删除其实没删干净"** 是这一类问题的共同特征——不报错、只是数据慢慢错。

## 4. 几个刻意的设计选择

### 4.1 监听"有变更就整库重扫"，不逐文件精确处理

`ScanJob` 的 diff 逻辑本来就是"遍历 + 比 sha256"，它自然会跳过未变的文件。

代价：每次变更都要遍历一遍目录（几百到几千个 `stat`，几十毫秒到几秒）。
收益：不需要维护第二套"变更 → 动作"的逻辑，也就不会出现"监听路径的判断与扫描路径的判断不一致"。

方案 §10.5 的目标是"改一个文件 30 秒内更新"，遍历完全够用（实测 0.1 秒）。

### 4.2 对账只标记，不自动删除

用户移动一次目录后，所有旧路径都不存在。自动删索引等于让他丢掉几小时的解析成果（重新扫描要重新解析）。

所以 `missing` 只标状态，由用户在提示条里选择"保留 / 移除 / 稍后"。

### 4.3 删除先删库记录、再动文件

反过来的话会出现"文件已删、记录还在"——来源卡片仍写着"可以打开原文"，而文件已经没了。

### 4.4 文件只到回收站，不做永久删除

误删不可逆，而这个产品没有任何撤销能力（无版本历史、无备份、无操作日志回放）。回收站是 Windows 自带的安全网，且不需要我们实现撤销栈。

`SHFileOperationW` + `FOF_ALLOWUNDO` 是资源管理器"删除"的同一个 API，行为与用户手动删完全一致。

### 4.5 只监听当前选中的库

同时监听所有库的目录会让事件量翻倍，且用户切库时仍会收到别的库的事件。切库时重启监听即可。

## 5. 一个测试基础设施问题（值得记）

M3 的三条对话测试在 M4 阶段突然失败，原因是**空闲卸载**：

```
idle.last_reason = 'model idle 9m11s, user idle 3m2s'
unloads_total = 1
```

我写完 M4 的代码（约 10 分钟）再跑测试，模型早被卸载了。表现是 `meta` 事件永远不来——实际是流一开始就返回 `model_unavailable`。

**这不是代码 bug，是测试没有自备前置条件。** 修复：加 `loaded_conn` fixture，需要模型的测试自己确保模型已加载（未加载就 load，load 失败就 skip）。

顺带暴露一个真实产品问题：**用户也会遇到同样的事**——离开一会儿回来提问就失败。这正是服务端待办 S10（启动加 `-preload`）的另一个佐证。桌面端已有 `check_chat_ready()` 会给出可行动提示。

## 7. 下一步（M5）

M5 是**打包与标定**：PyInstaller、安装器（含"已装 LocalAIHub 则跳过"）、首次引导、契约版本检查、**内存极限测试并回填 §10**。

M5 的验收是 A7（断网）、A8（8GB 机器）、A15（已装机器不重装）、A16（干净机器）。

**M5 之前建议先处理两件服务端待办**（否则"装完即用"不成立）：

- **S8**：安装时自动启用 Embedding 模型（否则装完语义检索不可用）
- **S10**：安装时加 `-preload`（否则重启后第一次提问失败）

这两条都是"改 `runtimeArgv` 一处即可"的小改动，但不做的话 M5 的"干净虚拟机装完即用"验收会失败。
