# 规模标定：10 万块完整向量化与检索

- **日期**：2026-11-16
- **规模**：**100100 块**（1 个库，600 篇 × 约 168 块）
- **目的**：确认设计上限（§10.3 的 10 万块）在真实硬件上是否可用
- **工具**：`tools/bench_scale.py --chunks 100000`
- **环境**：16 GiB / Windows 11 / CPU-only（无 GPU）

---

## 0. 结论摘要

| 指标 | 16016 块（前测） | **100100 块（本次）** | 缩放 |
| --- | --- | --- | --- |
| 入库 | 18.8 s | **84.1 s** | 4.5× |
| 向量化总耗时 | 1668 s | **10084 s（2.8 小时）** | 6.0× |
| 向量化速度 | 9.6 块/秒 | **9.9 块/秒** | 基本不变 |
| Runtime 内存（向量部分） | +66 MB | **+125 MB** | 1.9× |
| **热检索** | 469 ms | **1704 ms** | 3.6× |
| 冷启（首查） | 688 ms | **8156 ms** | 11.8× |

**三条必须接受的事实**：

1. **10 万块建库要 2.8 小时**（向量化），这是 CPU 上 384 维 embedding 的物理极限，
   不是 bug。所以"分阶段可用"不是优化项，是产品能否被用下去的前提。
2. **热检索 1.7 秒**，已明显超出门槛（~200 ms 是"瞬时"的心理边界）。UI 必须有
   可见的进度反馈，不能是"点了没反应"。
3. **冷启 8.2 秒**。这是索引载入（读 125 MB 向量 + 建索引）。首次提问必须
   明确提示"正在准备索引"，否则用户会以为卡死。

---

## 1. 向量化：2.8 小时，速度几乎不随规模衰减

| 规模 | 耗时 | 速率 |
| --- | --- | --- |
| 16016 块 | 1668 s | 9.6 块/秒 |
| 100100 块 | 10084 s | **9.9 块/秒** |

**速率基本不变**（甚至略快），说明向量化是**线性**的，没有 O(n²) 问题。
中途观察到的 7.7~8.5 块/秒是抖动，不是衰减趋势（最后又回到 9.9）。

这一条很重要：它意味着"给用户的剩余时间估算"可以放心用固定速率
（约 10 块/秒），误差在 ±15% 内。

### 与之前 5.9 万块那次（11.6 块/秒）的差异

那次只向量化了 9440 块就测了增量，速率样本小、且当时 embedding 引擎刚启动
（有预热效应）。本次 10 万块全程平均 9.9 块/秒更可信。

**建议按 10 块/秒 做产品文案**：

| 库规模 | 预计 |
| --- | --- |
| 1 万块 | 17 分钟 |
| 5 万块 | 83 分钟 |
| 10 万块 | **2.8 小时** |

## 2. 检索：1.7 秒，比预期更慢

| 轮次 | 冷启 | 热（5 个不同 query） | 热（同 query ×3） |
| --- | --- | --- | --- |
| 第 1 轮 | **8156 ms** | 1938 / 1953 / 1984 / 2063 ms | 1656 / 1656 / 1641 |
| 第 2 轮 | 1703 ms | 1688 / 1797 / 1765 / 1781 ms | 1704 / 1718 / 1735 |
| 第 3 轮 | 1687 ms | 1938 / 2031 / 1937 / 1782 ms | 1625 / 1672 / 1625 |

**热检索中位数 1704 ms，范围 1625~2063 ms。**

### 关键观察：只有**第一轮**的冷启特别慢

第 1 轮 8156 ms，第 2、3 轮的"冷启"却只有 1703 / 1687 ms——与热态一致。
说明：

- 8156 ms 是**真正的一次性成本**（读 125 MB 向量 + `LoadIndex` 建索引）
- 之后索引常驻，不会在查询间释放
- 所以用户只在**每次启动程序后的第一次检索**付这 8 秒

### 与 16016 块的对比（同样的测量方式）

| | 16016 块 | 100100 块 | 增量 |
| --- | --- | --- | --- |
| 热检索 | 469 ms | 1704 ms | +1235 ms |
| keyword 通道（同期实测） | 204 ms | 未测（库已清理） | — |

按 16016 块的通道比例（keyword 占 43%）外推，10 万块的 keyword 可能在
**700~800 ms**，向量部分约 900 ms。

> **遗憾**：本想对 10 万块做通道拆解，但标定库在脚本结束时已按默认策略
> 清理了。重跑需 2.8 小时，不值得。**下次标定务必加 `--keep`**——
> 已经写进脚本的备忘。

## 3. 内存

| 阶段 | Runtime RSS |
| --- | --- |
| 向量化前（只有 Runtime + SQLite + Embedding） | 225 MB |
| 向量化后 | **350 MB** |
| 增量 | **+125 MB** |

10 万块 × 384 维 × 4 字节 = **147 MB** 的纯向量数据。实测 +125 MB，
差异来自"向量存在 SQLite BLOB、索引另算"——说明实现是高效的
（没有额外的副本）。

对比 16016 块的 +66 MB：1.9 倍 vs 6.25 倍的块数，说明有固定开销在里面
（索引结构、页缓存）。

**桌面端预算不受影响**：这 125 MB 在 Runtime 侧，而 §10.0 的结论
（桌面端 100 MB）仍然成立。整机口径（Runtime + 模型 + 桌面端）在
**10 万块 + 3B 模型**时约 350 + 3318 + 100 = **3.8 GB**。

## 4. 对产品的直接影响

### 4.1 首次建库必须分阶段可用（已有结论，现在有量化）

```
10 万块建库 = 解析 5 分钟 + 入库 1.4 分钟 + 向量化 2.8 小时
```

**前 7 分钟之后关键词检索就能用了**，剩下 2.8 小时在补语义能力。
UI 必须能表达这个区别，否则用户会以为"软件卡了两小时"。

### 4.2 检索必须有进度反馈

1704 ms 已远超"瞬时"阈值。具体建议：

| 场景 | UI 行为 |
| --- | --- |
| 检索开始 | 立即显示"正在检索…"（不要让按钮看起来没反应） |
| > 1 s | 补一句"库较大（N 块），检索约需 2 秒" |
| 首次检索（索引未载入） | 显示"正在载入索引（首次检索较慢，约 8 秒）" |
| 超过 5 s | 提供"取消" |

**"首次检索 8 秒"这条尤其重要**：用户启动程序后第一个问题会等 8 秒，
如果不解释，他的结论是"这软件很卡"，而实际后续都是 1.7 秒。

### 4.3 10 万块上限要不要下调

**建议保留 10 万块**，理由：

- 内存不是问题（+125 MB）
- 检索 1.7 秒虽然慢，但可用（配合进度反馈）
- 向量化 2.8 小时是一次性成本，且分阶段可用

但要在 8 万块时提示："接近上限，语义索引补全约需 2 小时"。

如果将来用户抱怨检索慢，**先优化 FTS5**（10 万块预计占 700~800 ms），
而不是换向量索引——`vector.go` 的暴力扫描在 10 万块下约 900 ms，
换 ANN 收益不足以抵消复杂度（方案 §10.5 的判断仍然成立）。

## 6. 复现方法

```powershell
# 全量（约 3 小时）
python tools/bench_scale.py --chunks 100000 --keep

# 只测检索（库已在时）
python tools/bench_scale.py --kb-id <id> --search-only

# 小规模验证脚本（约 30 分钟）
python tools/bench_scale.py --chunks 10000
```

**加 `--keep` 才能保留库**，否则脚本结束时删除——本次就是因为没加，
无法再做通道拆解。
