## 3. 交付前确认的一个环境问题

**语义检索当时完全不可用**：`launch-spec.json` 里没有 `-embedding-model`，而管理后台只能**查看**该字段、不能修改（`admin.Config` 里它不在可改集合）。

表现为：`vectorize` 任务立刻失败，报"未配置 Embedding 模型，只能做关键词检索"。检索因此只有 `mode=keyword`。

**这不是代码缺陷**，是部署配置缺失。修法是改 `launch-spec.json`（运维动作，不是改产品）：

```json
{
  "v": 1,
  "args": [
    "serve", "-enable-admin",
    "-llama-server", "...\\engines\\llama-cpu\\llama-server.exe",
    "-embedding-model", "...\\models\\multilingual-e5-small-q8_0.gguf",
    "-models", "...\\models"
  ]
}
```

重启后 `vectorize.model` 变成 `multilingual-e5-small-q8_0`，语义检索可用。

**这件事说明一个产品缺口**：用户装完 LocalAIHub 默认**没有语义检索**，而管理后台无法开启它。建议记为服务端待办——让管理后台支持配置 Embedding 模型（或首次启动时自动探测 `models/` 下的 e5 并写入 launch-spec）。

## 4. 几个刻意的设计选择

### 4.1 切块结果缓存在 `ScanItem` 上，不重新解析

`parse_all` 把 `chunks` 存在 `item._chunks`，`ingest_all` 直接复用。

**为什么不重新解析**：一篇 500 页 PDF 解析要 8~15 秒，再解析一遍等于扫描时间翻倍。更糟的是文件可能在两次之间被改动，导致"入库的块"与"报告的块数"对不上——那种不一致极难排查。

**代价**：内存。296 块约几 MB，2000 块约几十 MB。与"翻倍扫描时间"相比值得。

### 4.2 入库失败用返回值，不用异常

```python
ok, fail = ingest(self._conn, self._kb_id, req)
if fail:
    if fail.needs_rebuild or fail.should_pause:
        break
    continue
```

扫描是"逐篇处理、单篇失败不中断"（§10.5）。用返回值让循环保持扁平，不必每篇套 try/except；而**需要中断扫描**的情况（资源不足、队列满、切块器版本冲突）用 `should_pause` / `needs_rebuild` 表达，比异常更直白。

### 4.3 两类错误必须暂停整次扫描

| 错误 | 为什么停 |
| --- | --- |
| `resource_limited` / `queue_full` | 是**系统状态**，不是这一篇的问题。继续提交只会堆队列 |
| `chunker_mismatch` | 库内版本不一致，后面每一篇都会同样失败。必须让用户决定是否重建 |

其余错误（单篇解析坏、单篇内容超限）继续下一篇。

### 4.4 2000 块在客户端预检

服务端也会拒绝，但那时客户端已经解析完整个文件（可能几分钟）。提前拦截省掉一次必然失败的往返与等待。数字与 `document.MaxChunksPerRequest` 保持一致。

### 4.5 增量更新必须带 `update_document_id`

`CHANGED` 且已有 `doc_id` 时才传。不传会新建一份重复文档——这是 §7.2 明确警告的。

服务端 `FindDocumentByHash` 会按 `file_hash` 去重，但改过的文件 `file_hash` 已经不同，所以去重救不了这种情况。

## 7. 与方案文档的偏差

| 方案原写 | 实际实现 | 原因 |

| 未提"切块结果要缓存" | `ScanItem._chunks` | 避免重复解析（见 §4.1） |
