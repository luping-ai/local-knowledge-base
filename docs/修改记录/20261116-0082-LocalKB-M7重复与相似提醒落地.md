## 2. 三个核心设计决定

### 2.1 完全重复与内容相似是**两条**提示，不合并

| | 完全重复 | 内容相似 |
| --- | --- | --- |
| 判据 | sha256 相同 | 文本指纹相近 |
| 需要用户判断吗 | **不需要**（内容一模一样） | **需要**（选哪一版） |
| 界面 | 一行灰色提示 + "详情" | 橙色提示 + "去确认" |
| 打断流程 | 不打断 | 结束时报一次 |

合并成一条会让用户以为"连一模一样的文件也要我逐个确认"——那是纯粹的负担。
方案 §12.2 把这两层分开的理由就是这个。

### 2.2 为什么必须优先保留"已入库的那份"

`_mark_duplicate` 在遇到 `sha256` 重复时，若库里已有一份 `imported`，
就把新的标为重复、指向旧的那份。反过来（保留新的、把旧的标重复）需要
先删已入库的文档再导一次——**白费几小时的向量化**。

实测验证：B1 的 5 份相同文件，第 1 份入库、后 4 份标 duplicate，
且 4 份都指向第 1 份。

### 2.3 换版本"先导后删"而不是"先删后导"

方案 §12.6 写的是"原版 delete 移除，新版 ingest 导入"，但**执行顺序要反过来**：

| 顺序 | 失败后果 |
| --- | --- |
| 先删后导 | 导入失败 → 用户从"有一版"变成"一版都没有"，**数据凭空消失** |
| 先导后删 | 删除失败 → 库里暂时两版都在，检索可能命中两版，但**数据没丢** |

两种失败里"多了一份"远比"少了一份"可恢复。

另外被换下的旧版标 `similar_replaced` 而不是 `excluded`：`excluded` 的语义是
"用户不要这个文件"（会被永久跳过，恢复要去设置页），而换版本是**可逆的**——
用户可能过两天想换回来。标成 excluded 会让"换回来"变成他不知道的两步操作。

## 3. 缺陷：`pending` 处理（方案 §12.4 的明确警告）

SDK docstring 写得很清楚，我实现了两条保护：

### 3.1 `recompute=True` 保证结论完整

快路径只对**已有指纹**的文档分组。刚导入的文档可能还没有指纹，它们会出现在
`pending` 里——此时"没有重复"这个结论是**不完整的**。

这个错误**没有任何症状**：界面正常、日志正常，只是结论错了。用户看到
"没有相似文件"就相信了，而实际上有 3 组正等着确认。

所以 `check_similar` 默认 `recompute=True`（5000 篇约 10 秒），并把
`pending` 数量写进说明文案。

### 3.2 空 `doc_ids` 必须拦住

服务端语义：`doc_ids` 为空 = "该库全部文档"。增量扫描时传空会让它做全库
重算（10 万块要几十秒），而 §12.5 明确要求"只对本次新入库的文档做"。

`check_similar` 里有一条显式返回：

```python
if not doc_ids:
    return SimilarResult(note="本次没有新入库的文档，跳过相似检测")
```

测试 `test_empty_doc_ids_skips_without_calling_server` 断言**没有调服务端**
（不只是返回空结果）——只看返回值无法区分"拦住了"和"调了但没分组"。

## 4. 待确认状态持久化（B8，产品底线）

§12.10 写"B8 是产品底线：待确认状态必须持久化。丢了比不提示更糟——
用户以为确认过了"。

实现要点：`pending_dups` 表的 `upsert_pending_group` 对 **`resolved=1` 的行
直接跳过**。先删后插会让用户已确认的组重新出现，他就再也不相信确认动作有用。

验证方式：`test_resolved_group_not_recreated` 先确认一组，再跑一次检测，
断言 `count_pending_groups == 0`。

端到端也验了"模拟重启"：新建一个 `StateDB` 连接读同一文件，组与成员路径都在。

## 5. B6 不通过：相似阈值对模板文档过严

这是本轮最重要的实测发现，详见
`docs/实测记录/20261116-相似阈值对模板文档过严.md`。

**现象**：8 份结构完全相同的填空合同：

| 文档长度 | 实际分组 | 期望 |
| --- | --- | --- |
| 235 字 | 1 组 2 个 | 1 组 8 个 |
| 660 字 | 2 组共 5 个 | 1 组 8 个 |

**根因**：`internal/knowledge/dedup/simhash.go` 的 `ThresholdShort = 2`，
而这个文件的注释自己写着"这些是初值，必须用标注集校准后回填"。

**处理方式**：不把验收标准改成"成 2 组也算过"。验收标准表达的是产品意图
（"用户应该能一次确认掉 8 个填空版"），改它会让功能失去意义。

验证脚本里如实报告：

```
[B6] 8 个填空版合同（应成组）
  [PASS] 检测出相似组  -> 2 组，共 5 个文件
    （注意：5/8 个文件成组，期望 8 个——阈值 ThresholdShort 偏严，见实测记录）
```

**为什么可以作为已知问题发布**：阈值偏严只会让用户多点几次"确认"，
**不会产生错误结果**。反方向（阈值过松）会导致用户确认后只入库一份，
另一份内容搜不到——那是不可逆的信息损失。

## 6. 两个我自己犯的错（写验证脚本时）

### 6.1 预选后差异不显示

`SimilarDialog._build()` 末尾只调了 `_sync_ok_state()`，没调 `_update_diff()`。
于是 `newest` 预选时，单选按钮选好了，但差异区还是"选中一个文件后…"的占位文字。

用户会以为差异功能没生效，或者以为预选的那份是"组内第一个版本"
（提示语正是这么写的）。

**只有截图能发现**：单元测试断言的是 `chosen_doc_id` 与 `btn_ok.isEnabled()`，
两者都对。是 `QWidget.grab()` 出来的图里那句占位文字暴露了它。

### 6.2 完全重复的说明文案给了一个无意义的建议

第一版写"如果你要搜的其实是某一副本，可以在资源管理器里把要用的那份
改成不同内容，或把它移到别的库"。

但**完全重复的文件内容一模一样**，搜哪一份结果都相同，换哪份入库对检索
没有任何影响。给一个"怎么换"的指引反而让用户以为这里有需要他决定的事。

改成说明"为什么这没影响"："这些副本与已入库的那份内容完全相同，所以
不入库也不会让你搜不到——检索命中的就是同一段内容。"

## 8. 与方案文档的偏差

| 方案原写 | 实际 | 原因 |
| --- | --- | --- |
| D1「随 M3 一起做」 | M7 才做 | M3 时只写了 SQL，扫描流程未接线 |
| 换版本「先 delete 再 ingest」 | **先 ingest 再 delete** | 失败后果可恢复性（见 §2.3） |
| 被换下的版本无状态定义 | 新增 `similar_replaced` | `excluded` 语义不符（那会永久跳过） |
| 提示条一处 | **两处**（重复 / 相似） | 两层决策性质不同（见 §2.1） |
| 无设置页 | 新增设置菜单（仅一项） | B10 要求"设置页可开 newest/oldest" |
| 无关于页 | 顺带加了"关于" | 菜单栏既已存在，加一项成本极低 |
