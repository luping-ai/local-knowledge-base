## 3. 安装与卸载的四个缺陷（都不是语法错误，都不会编译失败）

这一节的问题有共同点：**编译通过、安装成功、界面正常**，只有做具体的
比对才暴露。这也是为什么最后写了 `verify-installer.ps1`——把"比对"变成
每次发版都跑的断言。

### 3.1 简体中文语言包不在 Inno Setup 里

`.iss` 原本写 `MessagesFile: "compiler:Languages\ChineseSimplified.isl"`。
这看起来是官方路径，但——

Inno Setup 6 官方安装包只带 30 种语言，**简体中文不在其中**（属于官方
仓库里的 user-contributed 翻译）。编译直接失败：

```
Could not read "Languages\ChineseSimplified.isl"
```

修法：把 `.isl` 放进 `tools/` 一起入库，用 `{#SourcePath}` 相对引用。
好处是换机器、换 Inno 版本都能编译，不依赖目标机装了哪些语言包。

### 3.2 没有 BOM 的 UTF-8 → 中文界面乱码（静默）

`.iss` 与 `.isl` 都是 UTF-8 无 BOM。Inno Setup **只在有 BOM 时才按 UTF-8
解析**，否则按系统 ANSI 读。

后果不是编译错误，是**装的时候整个向导的中文变成乱码**。而开发机上
"能编译"掩盖了一切。

修法：两处都加 BOM；并且 `package-localkb.ps1` 每次都检查一遍
（不依赖"上次已经加过"）——因为 git 检出、编辑器另存都可能把 BOM 弄丢。

### 3.3 静默卸载删光用户数据（最严重）

这是本轮最值得记的一个。

**现象**：`unins000.exe /VERYSILENT /SUPPRESSMSGBOXES` 卸载后，
`%LOCALAPPDATA%\LocalKB\state.db` 消失了。

**第一层原因**：Inno Setup 文档写明——`/SUPPRESSMSGBOXES` 抑制消息框时，
**需要选择的场景默认响应是 Yes**。所以那个"要删除本地数据吗？"的对话框
在静默模式下等于自动点了"是"。

`MB_DEFBUTTON2` 完全没用：它只影响用户**看得见按钮**时的高亮位置。

**第二层原因（更隐蔽）**：修第一层时用了 `WizardSilent()` 判断是否静默，
编译通过、卸载"成功"、数据也"保留"了。但卸载日志里有一行：

```
CurUninstallStepChanged raised an exception.
内部错误：Cannot call "WizardSilent" function during Uninstall.
```

`WizardSilent()` 在卸载阶段**不允许调用**。数据之所以还在，是因为异常
提前中断了事件处理函数、恰好跳过了 `DelTree`——**巧合，不是正确**。
换个 Inno 版本、或异常被处理掉，就会退化成 3.3 的原始问题。

正确函数是 `UninstallSilent()`。用一次性探测脚本（造一个最小 `.iss`，
在 `InitializeUninstall()` 里 `Log('UninstallSilent=' + ...)`，实测
`/VERYSILENT` 下输出 `UninstallSilent=YES` 且无异常）确认后才敢用。

**影响面**：IT 部门用 `/VERYSILENT` 批量卸载、或脚本重装一次，用户的索引
就没了。下次打开要重新扫描整个目录（可能几小时），而且**事后无法恢复、
不会报错**。

### 3.4 附带：验收脚本自己的编码坑

`verify-installer.ps1` 第一版用 `Get-Content -Raw` 读 `selfcheck.txt`，
两条中文断言 FAIL、而 ASCII 断言全部 PASS。

原因：PowerShell 5.1 对**无 BOM** 的 UTF-8 按系统 ANSI 解码，中文全乱码。

这暴露出产品侧的真问题：`selfcheck.txt` 的读者是"遇到问题来找我们的人"，
他也会用记事本打开——同样会看到乱码。所以修的不只是脚本，产品也改成
`utf-8-sig` 写入，并加了 3 个测试锁住"必须有 BOM"这个属性。

**这个属性用 Python 读回来验不出来**（`read_text(encoding="utf-8-sig")` 两种
写法都能读），只有按字节看前 3 字节才能发现。

## 4. 启动流程的三个产品缺陷（截图与测试发现的）

这三个问题都没有任何报错，全部是"界面看起来正常但信息自相矛盾"。

### 4.1 启动时弹模态框 → 窗口"半画出来就卡死"

`_check_startup_prereq()` 第一版是：

```python
while True:
    chk = evaluate_startup(self._conn)
    if not chk.has_problem:
        return
    dlg = StartupDialog(chk)
    if dlg.exec() != StartupDialog.Accepted:
        ...
        return
```

三个后果：

| 后果 | 现象 |
| --- | --- |
| 窗口还没画出来就弹模态框 | 用户看到"程序启动就卡死" |
| UI 线程上做 3 次同步 HTTP | Runtime 忙时窗口冻结，连对话框都画不出来 |
| 无法自动化测试 | 全量测试卡 11 分钟、CPU 停在 16 秒、无任何输出 |

第三点最关键：**它说明这段代码没有任何自动保护**。而如果那台机器的模型
已加载，这段代码永远不进入模态分支，手工点一遍也发现不了——缺陷只在
"模型未加载"的机器上出现。

修法：整段改成**非阻塞**。检查结果变成对话页的常驻黄条（含"重新检查"与
"打开管理后台"两个按钮），启动流程不等待任何用户输入。`StartupDialog`
整个删掉——留着就是没有调用点的死代码，而下一个人会以为"启动时还会弹框"。

文件随之从 `startup_dialog.py` 改名为 `startup_check.py`：一个不再包含
对话框的文件叫 dialog 会误导。

### 4.2 黄条被后写的覆盖（preflight 警告丢失）

黄条只有一块，启动时两个来源会写它：

- `_run_preflight()`：版本警告（如"没有配置 Embedding，只能关键词检索"）
- `_check_startup_prereq()`：缺 Runtime / 缺模型

第一版 `_check_startup_prereq()` 在**没有问题**时也调 `show_banner("")`，
把刚写进去的 preflight 警告清掉。用户看到"黄条闪一下就没了"——而那条警告
正是"语义检索为什么不好用"的唯一解释。

改成"无问题时不碰黄条"后，测试又发现了**第二层**问题：两个问题**同时存在**
时仍是后写的覆盖先写的。真实场景是"内存紧张导致 RAG 降级（警告）+ 模型
未加载（问题）"，两条各自回答不同的问题，缺一条都会让用户误判。

最终：合并显示，空行分隔。

### 4.3 状态栏显示"能力模型"而不是"已加载模型"

离屏渲染截图里同一屏出现两句话：

```
黄条：  本地服务已连接，但没有加载对话模型，暂时无法提问
状态栏：模型：qwen2.5-3b-instruct-q4
```

直接矛盾。原因是 `_on_bootstrap_ready` 用了 `cap.rag_model`——它回答
"**这台机器能跑哪个**"，不是"现在跑着哪个"。

用户看到这种矛盾的第一个结论是"这软件在胡说"，然后不再相信任何提示。

修法：状态栏只接 `active_model()`；能力模型（能跑什么）放进 tooltip，
文案标成"本机能力上可加载"。黄条里的 `capability().reason` 也从
"服务返回的原因"改成"（本机能力评估：…）"并补一句"这不是报错"——
因为它其实是肯定语气的（"可用内存 4.4 GiB，可加载 3B 做问答"），
放在"未能提问"下面会自相矛盾。

## 5. 为什么需要离屏截图工具

验证"黄条长什么样"时先试了系统截屏，失败两次：

1. `SetForegroundWindow` 报成功，但截图还是别的窗口
2. 拿到 `MainWindowHandle` 后调用 `ShowWindow`，几秒后句柄变成 0，
   `GetWindowRect` 返回 `0x0`，截出来是空图

`QWidget.grab()` 是 Qt 自己渲染到 QPixmap——不依赖窗口是否可见、是否在
前台、是否被遮挡。`tools/shot-localkb.py` 用它，顺带把黄条文本与
`isHidden()` 打印出来，可以脚本化断言。

**这个工具直接发现了 §4.3 的矛盾**——两条信息在同一张图里，一眼就能看出
不对。而分别看代码或分别看文字日志时，两处都"看起来正常"。

---


`tools/verify-installer.ps1` 覆盖两类"手工装一遍看不出来"的问题：

### A15（同机复用一个 Runtime）

| 断言 | 为什么这么验 |
| --- | --- |
| `launch-spec.json` 未被改写 | 哈希 + mtime 双比。装第二份 Runtime 会重写这个文件 |
| 没有新增 localai 相关 Run 键 | 数条数而不是比整串（别的软件也在写 Run 键） |
| 没有启动第二个 Runtime | 记安装前 PID，装完必须完全一致（10112 → 10112） |
| 自检：`Runtime 连接` = OK | 端到端证据：真的按 discovery 找到并连上了 |
| 自检：`level=full` | 说明拿到的是完整能力，不是降级模式 |
| 自检：无 `[FAIL]` | 八项全过 |

**为什么用 `--self-check` 而不是看窗口**：截图无法自动判定"连的是哪个 PID"，
而自检把结果写进文件，可以逐行断言。

### 静默卸载保数据

| 断言 | 对应哪个缺陷 |
| --- | --- |
| 用户数据目录仍在 | 3.3 第一层（默认 Yes） |
| 用户数据**内容**未变（marker 比对） | 误删后重建空库也是"看起来正常" |
| 卸载脚本没有抛异常 | 3.3 第二层（`WizardSilent`） |
| 卸载日志记录「保留用户数据」 | 确认走的是预期分支，不是碰巧 |

## 6. 内存标定：修正与结论

### 修正了什么

旧版表格有三个不可能的数字，根因是**测量期间 Runtime 状态在变**：

| 旧值 | 原因 | 修正后 |
| --- | --- | --- |
| 每块向量内存 **-0.052 MB** | 向量化跑了 8000 秒，期间模型被空闲卸载，RSS 从 3407→302 | **+0.001 MB/块** |
| 向量化 7.4 块/秒 | 同上，被卸载打断 | **11.6 块/秒** |
| 提问回答 0 字 | 模型已被卸载，请求失败 | 27 秒，正常回答 |

修法：**向量化前显式 `unload_model()`**，拿到"只有 Runtime + SQLite +
Embedding"的干净基线，再测增量。

**教训**：测 Runtime 内存必须先固定它的状态。模型加载/卸载造成 3 GB 波动，
足以淹没任何精细测量。

### 最重要的结论：方案对 PyMuPDF 的估算偏高 50 倍

| 项 | 方案 §10.1 估 | 实测 |
| --- | --- | --- |
| 解析 500 页 PDF 的增量 | 150~250 MB | **+5 MB** |
| 桌面端总预算 | 358 MB | **100 MB 足够**（留 3.5 倍余量） |

原因是 PyMuPDF **按需分页**，不把整份文档解压进内存。方案里的估值大概来自
"一次性 `get_text()` 全文档"的用法。

这一条直接影响产品行为：原本担心"解析大文件会与推理撞车"，实测不会。

### 真正的瓶颈：向量化 11.6 块/秒

| 库规模 | 一次性建库 |
| --- | --- |
| 1 万块 | 14 分钟 |
| 5 万块 | 72 分钟 |
| 10 万块 | 2.4 小时 |

这不是 bug（CPU 上 384 维 embedding 就是这个量级），但它决定了**首次建库
必须分阶段可用**：

1. 解析阶段就可检索：每篇解析完立即入库，**关键词检索立刻可用**
2. 向量化在后台：显示"语义检索准备中（3000/60000）"，不阻塞提问
3. 明确告知剩余时间：用实测 12 块/秒估算
4. 允许中断：`vectorize` 本来就分批落库，已完成的保留

提示语不能写"正在建立索引"，要写"正在生成向量 3000/50000（约 65 分钟）"。

### 检索耗时：推翻了两条既有目标

用一个专门工具（`tools/bench_scale.py`）建 16016 块的库并分段测量，
结论是方案 §10.5 的目标定错了两次。

| 通道 | 16016 块（热） | 296 块（热） |
| --- | --- | --- |
| `keyword`（纯 FTS5） | **204 ms** | 86 ms |
| `semantic` 多出的部分 | ~150 ms | ~23 ms |
| `hybrid` 合计 | **469 ms** | 140 ms |
| 冷启（含 `LoadIndex`） | 688 ms | — |

三个判断：

1. **"检索 < 50 ms" 永远不可能达成** —— 仅 HTTP + FTS5 的固定成本就 86 ms
2. **`LoadIndex` 不是问题** —— 冷启只比热多 219 ms；第 2、3 轮的"冷启"
   （485 / 422 ms）与热态几乎无差，说明索引稳定驻留，不会在查询间释放
3. **不要优化向量索引** —— 如果扫描是瓶颈，冷启不会这么接近热态。
   `internal/knowledge/vector/vector.go` 的连续 `[]float32` + 8 路并行足够

**真正值得优化的是 FTS5 查询本身**（`LIMIT` / 排序策略）——它是唯一随规模
线性增长的部分，而之前被当成"固定几毫秒"。

### 一个省时间的实验设计

keyword 通道不依赖向量，所以"只入库、不向量化、只测 keyword"能在
**35 秒**内走完 4 个规模档位。同样的曲线用完整流程做要 2 小时以上。

```
2002 块  → 110 ms
5005 块  → 109 ms
10010 块 → 156 ms
16016 块 → 204 ms
```

这也是发现"FTS5 随规模变慢"的手段——它直接把怀疑范围从"整个检索链路"
缩到"FTS5 一侧"。

### 缺陷：用估算值控制循环次数，导致规模失控

`bench_scale.py` 第一版这样算篇数：

```python
per_doc = 89                      # 从 chars_per_doc=40000 反推的估算
docs_needed = target // per_doc
for i in range(docs_needed): ...
```

而真实值是 **168 块/篇**，差了近一倍。后果：

| 现象 | 影响 |
| --- | --- |
| pilot 想造 1 万块，实际入 16016 | 数字对不上规格 |
| 10 万块那次跑到第 500 篇已 67353 块；按 1123 篇算最终 **18.8 万块** | 不是"设计上限"，而是 1.9 倍 |
| 向量化时间 2.9 h → 5.4 h | 多烧 2.5 小时 |
| 内存数据偏高近一倍 | 会得出错误的预算 |

**更值得注意的是：pilot 阶段已经暴露过这个偏差（1 万 → 16016），我看到了
但没修就启动了大规模。** 小规模测试暴露的偏差，如果只是"记一笔"，那这次
测试就白做了——它本该是"修完再放大"的信号。

修法：每轮向服务端要实际的 `kb_stat` 块数，达到 target 就停。估算值只用于
打印提示，不参与循环控制。代价是每篇多一次 HTTP（约 10 ms，相对入库的
2 秒/篇可忽略）。

修复后重跑：**100100 块，精确命中目标**。

## 7. 打包脚本的签名顺序修正

第一版把代码签名放在**最后**（`[5/5]` 之后）。这有两处错：

1. 清单里的 `entrySha256` 记录的是**签名前**的哈希 → 与实际文件对不上
2. `Setup.exe` 在编译时已经把未签名的 exe 打包进去了 → 装出来还是未签名

现在顺序是：

```
裁剪 → 签 exe → 冒烟（验签名没弄坏它）→ 清单（记签名后哈希）
     → 编译 Setup.exe（自然带已签名 exe）→ 签 Setup.exe（签完重算哈希）
```

**Setup.exe 必须单独签**：用户双击的是它。未签名的 Setup.exe 会被
SmartScreen 直接拦下，里面那个已签名的 LocalKB.exe 根本没机会被看到。

## 8. 与方案文档的偏差

| 方案原写 | 实际 | 原因 |
| --- | --- | --- |
| 安装包含 Runtime 或引导安装 Runtime | **都不含**，只检测 + 提示 | §3.1 复用已装实例；"未装时代装"需要 LocalAIHub 的静默参数，属 A16 |
| 桌面端内存 358 MB | **100 MB** | 实测偏高 50 倍，见 §6 |
| 单 PDF 上限 500 页 | 可放宽到 **1000 页**（+10 MB / 9 秒） | 实测支撑 |
| 卸载"询问后删除数据" | **静默卸载一律不删** | §3.3 |
| 首次启动"多步向导" | **无向导**，只在有问题时显示黄条 | §4.1：向导要么第二次还要看一遍，要么要维护会失效的"已完成"标记 |
