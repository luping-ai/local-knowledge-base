## 3. 五个真实缺陷

### 3.1 `capability()` 说能对话，实际没有模型

**这是最贵的一个。**

`capability()` 返回 `chat_enabled=true`、`rag_enabled=true`、`level=full`，但提问直接得到：

```
model_unavailable: 没有已加载的模型，请先通过 POST /api/v1/models/load 加载
```

**根因**：`capability` 是**启动时**算的静态判断（"这台机器能不能跑"），而"现在有没有模型加载"是另一回事。Runtime 重启后不会自动加载模型（除非启动参数带 `-preload`）。

**为什么难发现**：开发期一直有模型加载着（前一步 M2 用过），重启 Runtime 后忘了。而错误信息是英文原始码，直接透到用户面前。

**修复**：新增 `check_chat_ready()`，三档检查（`chat_enabled` → `active_model()` 空 → 通过）。失败时把原因写进**气泡位置**（不是底部小字），并给出可行动作（"去管理后台加载"）。

**这条也说明 §7.4 的"预热"策略需要加强**：不只是"知识库 READY 后预热"，而是**启动时就应确认模型已加载**，否则第一次提问必然失败。

### 3.2 知识库下拉框与实际选择不一致

**症状**：下拉框显示"不使用知识库"，旁边标签显示"localkb-dev"——界面自相矛盾。

**根因**：下拉框只有"不使用"与"全部"两项，"指定几个库"只能通过按钮进入。代码里 `set_scope(SELECTED, [...])` 时 `findData(SELECTED)` 返回 -1，`setCurrentIndex` 不执行，停在原项。

**修复**：下拉框加"指定的知识库…"选项，与 `KbScope` 的三个 mode 一一对应。

**这类"状态与实际不一致"的缺陷不会报错**，只会让用户困惑，而截图是唯一能发现它的手段。

### 3.3 SQLite 外键默认关闭 → 删会话留下孤儿消息

**症状**：`delete_conversation()` 之后 `list_messages()` 仍返回两条。

**根因**：SQLite **默认不强制 FOREIGN KEY 约束**，所以 `on delete cascade` 在没有 `pragma foreign_keys=on` 时完全无效。不报错，只是库文件慢慢变大。

**修复**：Open 时 `pragma foreign_keys=on`，并加测试 `test_foreign_keys_are_enabled` 锁定这一行。

### 3.4 每次启动都新建空会话

**症状**：用几次后会话列表全是"（未命名会话）"，真正有内容的被挤下去。

**修复**：`_resume_or_new_conversation()`——恢复最近一个**有消息**的会话；都没有才新建。跳过空会话的理由是"上次点开程序没提问就关了"，恢复它没有价值。

### 3.5 截断与换行把测试数据搞乱

`_trim` 折叠空白时把 `\n\n` 变成单个空格，而来源片段本来想保留段落感。这不是 bug（片段本来就是提示性的），但**测试里用 `\\n` 而非真实换行**导致过两次误判，已改成直接构造文本。

## 4. 两个刻意的设计选择

### 4.1 来源在 `meta` 就渲染，不等 `done`

`meta` 一定在第一个 delta 之前到达，而 `done` 可能永远不来（用户取消、网络断）。若等 `done` 才显示来源，中途失败时用户看不到任何依据——而那时他更需要知道"系统本来打算引用什么"（方案 §6.5）。

### 4.2 文件不在时用"查看片段"而不是灰掉按钮

用户移动一次目录后，每次看历史消息都会遇到"文件不在"。灰掉按钮等于告诉他"这条记录没用了"，而实际上库内内容仍可检索、片段也在快照里。

第三种终态是方案 §7.7.2 明确要求的，实现时很容易漏。

## 5. 发现的服务端缺口（已记为 S9）

`KnowledgeSource` **不含片段正文**，只有 `source` / `page_start` / `heading_path`。

而来源卡片要显示"引用了哪一段"（方案 §2.1 的示意图）。

**当前绕过**：`fetch_snippets()` 用同样的问题再 `search()` 一次，从 `hitResult.text` 拿片段。代价是每次提问多一次检索（10~30ms）。

**为什么还是要记为缺口**：重新检索拿到的片段**未必是模型实际用的那一段**（top_k 取前几条，可能错位）。服务端在 `KnowledgeSource` 里加 `text` 是更准确的方案。
