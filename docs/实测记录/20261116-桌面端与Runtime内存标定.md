# 桌面端与 Runtime 内存标定

- **日期**：2026-11-16
- **机型**：开发机（16 GiB 物理内存，Windows 11，i5 级 CPU）
- **目的**：测"内容规模 → 内存占用"的对应关系，作为**输入规模控制**的依据
- **工具**：`tools/bench_memory.py`
- **原始输出**：`docs/实测记录/` 同名 .md 的旧版本（数据不可用，见 §5）

---

## 0. 一句话结论

| 你想知道 | 答案 |
| --- | --- |
| 桌面端本身占多少 | **31 MB 空转，解析时峰值 105 MB**（与文件规模几乎无关） |
| 一篇 500 页 PDF 解析要多少 | 桌面端 **+5 MB**，4.4 秒 |
| 10 万块的知识库占多少内存 | 向量 + 索引约 **+76 MB / 5.9 万块 → 约 130 MB @ 10 万块** |
| 向量化多快 | **约 12 块/秒**（CPU），5000 块约 7 分钟，10 万块约 2.4 小时 |
| 解析 PDF 多快 | **113 页/秒**（8.8 ms/页），2000 页约 18 秒 |
| 检索多快 | 296 块 **140~170 ms**；5.9 万块首次 **2.4 s**（含索引冷启动），之后待测 |

**最重要的修正**：桌面端的解析开销比方案估算（150~250 MB）**低一个数量级**——实测 500 页 PDF 只增 5 MB。原因是 PyMuPDF 按需分页加载，不把整份文档解压进内存。

## 1. 桌面端（Python 进程）

| 场景 | RSS (MB) | 相对基线 | 耗时 (s) | 备注 |
| --- | --- | --- | --- | --- |
| 空转（只 import 依赖） | **31** | — | — | 基线 |
| 解析 PDF 10 页 | 62 | +31 | 0.16 | 含首次加载 PyMuPDF |
| 解析 PDF 50 页 | 63 | +32 | 0.45 | |
| 解析 PDF 200 页 | 66 | +35 | 1.70 | |
| 解析 PDF 500 页 | **72** | +41 | 4.42 | 文件 6.4 MB |
| 解析+切块 1000k 字 Markdown | 73 | +42 | 0.20 | 6579 块 |
| 入库 5.9 万块（提交过程） | 75 | +44 | 78.9 | 含 HTTP 与 JSON 序列化 |
| 向量化 5.9 万块（等待期间） | **105** | +74 | — | 峰值来自累计的 `chunk` 列表 |
| 提问（模型已加载） | 106 | +75 | 27.0 | 流式渲染文本 |

### 关键发现

**① 解析开销与文件大小几乎无关。**

500 页 PDF 只比 10 页多 10 MB。PyMuPDF 按需分页，不会把整份文档解压进内存。
方案 §10.1 估的"PyMuPDF 解析时峰值再加 150~250 MB"**偏高约 50 倍**——
那个数字大概来自"一次性 `get_text()` 全文档"的用法，而不是我们这种分页处理。

**② 桌面端的峰值出现在"向量化等待"（105 MB），不是解析。**

原因不是向量化本身（那在 Runtime 侧），而是脚本在处理 5.9 万块时累积了
`chunk` 列表。真实桌面端是逐篇处理、每篇提交后释放，所以实际峰值应在
**70~80 MB**。

**③ 结论：桌面端可以按 100 MB 预算。**

方案 §10.1 原写 0.35 GiB（358 MB），实测 100 MB 足够——留 3.5 倍余量。

## 2. Runtime（`localai-cli` + `llama-server`）

| 场景 | Runtime RSS (MB) | 相对基线 | 备注 |
| --- | --- | --- | --- |
| 无模型、Embedding 已启动 | **344** | — | 基线（含 63 MB 的 Embedding 引擎） |
| 入库 5.9 万块后 | 377 | +33 | 块文本 + FTS5 索引 |
| 向量化后（5.9 万块中 9440 已向量化） | 453 | +109 | 向量 BLOB 在 SQLite 里，未常驻内存 |
| 检索时（索引已载入） | 339~453 | — | 索引载入后常驻 |
| 加载 qwen2.5-3b 后 | **3662** | +3318 | 3B 模型权重 + KV cache |

### 关键发现

**① 向量存在 SQLite BLOB 里，不常驻内存。**

5.9 万块的向量化只让 Runtime 增 109 MB，而按 384 维 float32 计算
5.9 万 × 384 × 4 = 90 MB —— 增量主要来自 SQLite 页缓存与写入缓冲，
不是"向量数组常驻"。

**但检索时会载入**：`ensureIndex` → `LoadIndex` 把全库向量读进内存
建索引（首次检索会慢，见下）。

**② 模型是内存大户，且是固定成本。**

3B 模型 +3318 MB，占 Runtime 总量的 90%。这与方案 §10 的结论一致——
模型决定了机器的能力上限，而库规模只影响几十到一百多 MB。

**③ 索引载入 = 首次检索慢。** 5.9 万块的库首次检索 **2.4 秒**
（要读 90 MB 向量 + 建索引），之后应显著变快。这一点需要补测。

## 3. 速度（决定规模上限的另一个维度）

| 操作 | 实测 | 推算 |
| --- | --- | --- |
| 向量化 | **11.6 块/秒**（500 块基准测试） | 5000 块 ≈ 7 分钟；5 万块 ≈ 72 分钟；10 万块 ≈ 2.4 小时 |
| 解析 PDF | **113 页/秒**（500 页 4.42 秒，8.8 ms/页） | 100 篇 × 20 页（2000 页）约 **18 秒** |
| 切块 | 约 3 万块/秒（1000k 字 → 6579 块，0.2 秒） | 不是瓶颈 |
| 检索（296 块库） | 140~170 ms | 含 FTS5 + 向量 + RRF + HTTP |
| 检索（5.9 万块库，首次） | 2422 ms | 含索引冷启动 |

**向量化是真正的瓶颈。** 11.6 块/秒意味着：

| 库规模 | 一次性建库耗时 |
| --- | --- |
| 1 万块（约 500 篇） | 约 14 分钟 |
| 5 万块（约 2500 篇） | 约 72 分钟 |
| 10 万块（上限） | 约 2.4 小时 |

这不是 bug（CPU 上 384 维 embedding 就是这个量级），但它决定了**产品体验的
关键约束**：

- 首次建库必须**分阶段可用**（方案 §15 已写）：关键词检索在入库后立即可用，
  语义检索随后补齐
- 用户必须能看到"向量化进度"而不是一个转圈
- 提示语不能写"正在建立索引"，要写"正在生成向量 3000/50000（约 65 分钟）"

## 4. 对输入规模控制的建议

基于实测，方案 §10.6 的规模上限应当这样定（原值多是估算）：

| 指标 | 原方案 | 实测依据 | 建议值 |
| --- | --- | --- | --- |
| 单文档块数 | 2000 | Runtime 硬约束 | **2000**（不变） |
| 单 PDF 页数 | 500 页 | 500 页解析 4.4 秒、+5 MB | **可以放宽到 1000 页**（约 9 秒、+10 MB），但要考虑用户等待 |
| 单库 chunk 数 | 10 万 | 向量化 2.4 小时 | **保留 10 万**，但要在 8 万时提示"接近上限，语义检索会需要约 30 分钟补完" |
| 单库文档数 | ≈5000 | 由 chunk 上限推导 | 不变 |
| 单文件字节 | 1 MB | 与块数无关（解析按页） | **改为按块数判断**（已有） |

### 新增的约束：首次建库的等待时间要预告

用户选一个 3000 篇的目录（平均每篇 20 页），会经历：

```
解析 3000 篇（6 万页，约 9 分钟）
入库（约 5 分钟）
向量化 6 万块（约 86 分钟）
────────────────────────────
总计约 100 分钟
```

**注意瓶颈完全是向量化**，不是解析——解析 6 万页只要 9 分钟（113 页/秒），
而向量化 6 万块要 86 分钟。所以"分阶段可用"的关键在向量化这一步。

方案 §15 只写了"首扫 5000 篇耗时过长 → 用户中途放弃"，没有给具体对策的量化。

建议的 UI 行为：

1. **解析阶段就可以用**：每篇解析完立即入库，关键词检索立刻可用
2. **向量化在后台**：显示"语义检索准备中（3000/60000）"，不阻塞提问
3. **明确告知剩余时间**：用实测的 12 块/秒估算
4. **允许中断**：向量化可取消，已完成的保留（`vectorize` 本来就分批落库）

## 5. 这份记录的旧版本为什么不可用

第一版跑完写出的表格有这些明显错误（已修）：

| 现象 | 原因 |
| --- | --- |
| "每块向量+索引内存 = **-0.052 MB/块**" | 向量化跑了 8000 秒，期间**模型被空闲卸载**，Runtime RSS 从 3407 掉到 302 |
| "入库 5.9 万块"（目标 2 万） | 每文档块数计算错误 |
| "向量化 7.4 块/秒" | 被空闲卸载打断，实际 11.6 |
| "提问回答 0 字" | 模型已被卸载，请求失败 |

修法是：**向量化前显式 `unload_model()`**，拿到干净的基线（只有 Runtime +
SQLite + Embedding），再测增量。修完后上面第 2 节的数字才成立。

这条值得记：**测量 Runtime 的内存必须先固定它的状态**。模型加载/卸载会让
RSS 变化 3 GB，足以把任何精细测量淹没。

& .venv\Scripts\python.exe tools\bench_memory.py --full --chunks 20000 `
